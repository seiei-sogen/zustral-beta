= issue #38 の修正計画: リテラルの形を、型検査まで運ぶ

== 目的

issue #38 は、16進、2進、8進、文字のリテラルが構文解析で10進の整数の文字列になり、型検査が元の形を知らないことを報告している。
Decimal の仕様（`docs/decimal.md` の3.1節）は、10進でない形のリテラルと指数のあるリテラルを、Decimal にしない。型検査がこれを断るには、リテラルの形が型検査まで届く必要がある。

終わりの条件は、`docs/plan.md` の L4 のとおりである。型検査が、どの位置のリテラルについても、書いた形（10進、16進、2進、8進、文字）、書いたままの文字列、小数部の桁数、指数の有無を読めること。整数の位置での挙動は変えない。

== 現状

作業の基点（`607d9b55`）で確かめた。

* リテラルの記録は、すでにある。リファクタリング R18（issue #111）が、`lib/NumberLiteral.ml` の `int_literal`（書いた文字列、形、値）と `float_literal`（書いた文字列、小数部の桁数、指数の有無）を作った。構文解析が記録を作り、型検査までのすべての段が、それをそのまま運ぶ。issue の本文の「10進の整数の文字列になる」は、もう起きない。
* 残っていたのは、単項の `-` である。符号は演算子なので（issue #48）、結合の段が、リテラルの前の `-` をリテラルに読み込む（`LiteralTyping.negation_of_operand`）。整数のリテラルでは、このとき記録を値から作り直していた（`NumberLiteral.of_value`）。`-#xFF` は、型検査には、10進で `-255` と書いたリテラルに見えた。`-'a'` は `-97`、`-1'000` は `-1000` に見えた。小数のリテラルは、`negated_float` が形を保っていた。
* issue の再現のプログラム（`let x: Int32 := 'a'; printLn(x);`）は `97` を出力する。issue のとおり、整数としては意図した挙動である。外から見える動きに、不具合はない。

== 変更

* `lib/NumberLiteral.ml`: `negated_int` を足す。値の符号を反転し、書いた文字列の先頭の `-` を付け外しする。形はそのままである。文字列の付け外しは、`negated_float` と共通の `toggle_leading_minus_of_written_text` にまとめる。
* `lib/LiteralTyping.ml`: `negation_of_operand` が、整数のリテラルに `negated_int` を使う。
* 生成する C は変わらない。C の表記は値から作る（`CIntegerConstant.text_of_value`）。収まらないときのエラーも、値を出す（`NumberLiteral.int_text`）。

== テスト

最初に書く、失敗するテスト。

* `test/TypeCheckExprTest.ml` の `test_literal_form_reaches_the_type_checker`: 式の文字列を構文解析し、結合の段の式の変換（`AbstractionPass.abs_expr`）を通し、型検査にかける。型検査の返す節の記録が、書いた形を持つことを確かめる。`#xFF`、`-#xFF`、`-(-#xFF)`、`-#b101`、`-#o17`、`-'a'`、`-1'000`、`-1.50`、`-1.5e3` である。直す前は、`-#xFF` の書いた文字列が `-255` で、失敗した。

挙動が変わらないことを固定するテスト。

* `test-programs/suites/035-literal-forms/035-negated-literals-of-every-form`: `-` を付けた16進、2進、8進、文字、桁区切りのある10進のリテラルを、`let`、定数、引数、`if` 式の枝、演算子の相手に書く。`-#x80` が `Int8` に収まることも見る。直す前と後のコンパイラで、出力も生成した C も同じだった。

== 確認

* 計測値: `lib/NumberLiteral.ml` が5行増える。`measure.sh --record` で記録し直した。
* エラーメッセージのテスト: 文面は変えていない。
* カバレッジ: `negated_int` と `toggle_leading_minus_of_written_text` の2つの枝は、上の2つのテストが実行する。
* 等価性: `tools/refactoring/check.sh 607d9b55 --quick` で、リポジトリのすべてのプログラムの生成した C を、基点と比べる。

== 範囲外

* リテラルだけの式の畳み込み。`#x10 + 1` は、型検査の前に畳み込まれて、10進で `17` と書いたリテラルになる。型検査には、元の `#x10` が見えない。畳み込みを型検査の後ろへ移すのは、L5（issue #37）である。そこで、型検査が元のリテラルを1つずつ見られるようになる。ここで畳み込んだ値に印を付けても、L5 で消える。
* 形を使う検査。10進でない形を Decimal の位置で断るのは、D2 と D3 である。

== セルフレビュー

issue の本文と `docs/plan.md` の L4 に照らして見直した。

* 「元の形を持たせる」: 構文解析が作る記録は、R18 で形を持っていた。`-` を付けたリテラルも、形を保つようにした。
* 「整数の位置での挙動は変えない」: 生成する C は値から作る。新しいスイートの出力と生成した C は、直す前と同じである。
* 「型検査が `#xFF` と `255` を区別できる。小数部を何桁書いたかが分かる」: 型検査の単体テストが、型検査の返す節を見る。
* 位置: 型検査の入口に記録を表示する仕掛けを入れたコンパイラ（作業用の写しで、コミットしない）で、`let`、定数、引数、演算子の相手、比較の相手、`if` 式の枝、スパンの添字に、すべての形を書いて確かめた。形は、10進、桁区切り、16進、2進、8進、文字（`'\n'` と `'\t'` を含む）、`-` 付き、`-(-…)`、`+` 付き、小数、指数付き、`5.` である。どれも、書いた形のまま型検査に届いた。`+24` は `24` として届く。`+` は演算子で、リテラルの一部ではないからである。届かなかったのは、畳み込んだ `#x10 + 1` だけである（範囲外）。
* `-(-#xFF)` は、書いた文字列が `#xFF` になる。小数の `negated_float` と同じく、先頭の `-` を付け外しするからである。値は 255 で正しい。
