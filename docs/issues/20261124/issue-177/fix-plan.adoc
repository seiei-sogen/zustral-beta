= issue #177 の修正計画: 線形性の検査を、関数の中の変数の数の3乗で遅くしない

== 目的

issue #177 は、線形性の検査が、1つの関数の中の変数の数の3乗で遅くなることを報告している。
#143 のプログラムは `main` に変数を N 個置くので、型が 400 個から 800 個になると、コンパイルがまだ 4.2 倍かかる。

終わりの条件は、次の2つである。

* 1つの関数の中の変数を2倍にしても、線形性の検査にかかる時間は、ほぼ2倍にしかならない。
* 受けるプログラムと断るプログラムは変わらない。エラーの文面と位置も変わらない。

== 現状

`d69429b`（#179 の変更を含む作業中の木）で確かめた。

関係するコードは、`lib/LinearityCheck.ml` である。

* `check_expr` は、式ごとに、表のすべての変数について `check_var_in_expr` を呼ぶ。`check_var_in_expr` は、その変数が式に何回現れるかを数えるために、式を1回たどる（`count`）。
* 表（`state_tbl`）はリストである。`get_entry` は、表を先頭から探す。式に現れない変数でも、状態を読むために表を探す。
* 式の数も、表の変数の数も、関数の中の変数の数 N に比例する。1回の探索も N に比例する。だから、N の3乗になる。
* `if` 文の後の `tables_are_consistent` は、片方の表の変数ごとに、もう片方の表を探す。`if` 文を変数ごとに置いた関数でも、N の3乗になる。issue には書かれていない、同じ原因の形である。

測ったプログラムは、`generate-program-with-many-variables-in-one-function.py`（この計画の隣）が書き出す。形は3つである。

* `variables-in-main`: #143 のプログラム。レコードを N 個宣言し、`main` に変数を N 個置く。
* `function-per-type`: 型ごとに小さい関数を1つ持つ。`main` に変数はない。比べるための形である。
* `if-after-each-variable`: `variables-in-main` の各変数の後に、`if` 文を置く。

1回の測定は、次の形である。コンパイル全体の利用者 CPU 時間を測った。

[source,sh]
----
python3 docs/issues/20261124/issue-177/generate-program-with-many-variables-in-one-function.py variables-in-main 1600 > p.zum
./zustral compile p.zum --entrypoint=Test:main --target-type=c --output=p.c
----

5 回の中央値で、括弧の中は最小と最大である。負荷は、4 コアに 3.5 から 8 だった。

[cols="2,1,1,1,1"]
|===
| 形 | 200 | 400 | 800 | 1600

| `variables-in-main` | 0.081 秒 | 0.217 秒 | 0.813 秒 | 5.276 秒（4.890 から 5.369）
| `function-per-type` | 0.076 秒 | 0.146 秒 | 0.295 秒 | 0.671 秒
| `if-after-each-variable` | 0.193 秒 | 0.979 秒 | 6.794 秒 | 50.212 秒（49.327 から 53.097）
|===

`variables-in-main` は、800 個から 1600 個で 6.5 倍、`if-after-each-variable` は 7.4 倍になる。

callgrind で、`variables-in-main` の 800 個を数えた。命令の 70.5% が線形性の検査で、69.9% が `check_expr` の中にある。そのうち 68.4% が `get_entry` である。式をたどる `count` は小さい。

== 変更

`lib/LinearityCheck.ml` だけを変える。

* 表を、名前から引ける表（`IdentifierMap`）にする。行は、型と状態と、その行を最後に変えた変更の番号（`row_last_change`）を持つ。変数を足すときと、状態を変えるときに、番号を1つ進める（`set_variable_as_latest_change`）。
* 表を順に並べる `table_rows` は、番号の大きい順に並べる。リストだったときの順と同じである。リストは、変数を足すときも、状態を変えるときも、その変数を先頭に置いていた。外していくときは、残りの順を変えなかった。どの変数をエラーで名指すかと、ループのエラーが変数を並べる順は、この順で決まる。
* 式をたどるのを、式ごとに1回にする。`count` を `count_appearances_of_variables` にし、式が使う変数のそれぞれが何回現れるかを、1回でまとめて数える。結果は、変数から現れ方への表（`appearances_by_variable`）である。式が使わない変数は、入らない。
* 2つの部分の現れ方をまとめる関数（`merge` と `merge_if_expression_branches`）は、変えない。`combine_by_variable` が、変数ごとに呼ぶ。片方の部分が使わない変数は、その部分では 0 回として渡す。前と同じ組で呼ばれる。
* `check_expr` は、式が使う変数だけを、表の順に調べる。式が使わない変数は、0 回現れるので、状態が変わらず、エラーにもならない。だから飛ばせる。表にない名前（`for` 文の変数）は、前と同じく調べない。
* 実行されなくなる腕を消す。式が使う変数は、少なくとも1回現れる。`partitions` の `Zero` と、`check_var_consumed_on_every_path` の `Zero` の4つの腕と、`in_right_operand_evaluated_on_some_paths` の 0 回の枝を消す。issue が心配していた「match の腕が、どのテストからも実行されなくなる」は、型から `Zero` を消して解く。

== テスト

振る舞いは変えないので、変わらないことを固定するテストを先に書く。どちらも `test-programs/suites/006-linearity` に置き、`d69429b` で通る。

* `044-error-names-the-variable-changed-last`: 1つの式が、消費済みの線形の変数を2つ使う。エラーは、最後に状態が変わった `zeta` を名指す。名前の順でも、宣言の順でも、式の中の順でも、`alpha` になる。
* `045-loop-error-lists-the-variable-changed-last-first`: ループが線形の変数を2つ消費する。エラーは `zeta, alpha` と並べる。

2つのテストが順の誤りを見つけることは、実装の並べ方を逆にして確かめた。`check_expr` の並べ方を逆にすると 044 が、`table_rows` の並べ方を逆にすると 045 が、失敗した。

速さを固定するテストは置かない。リポジトリに、時間の上限を持つテストの置き場がない。#143 の修正（Z16）も置いていない。代わりに、測ったプログラムの生成器を、この計画の隣に置く。

== 確認

* 生成した C: 3つの形の 200 から 1600 で、前と後のコンパイラが書いた C は、バイト単位で同じである。
* base との等価性: `tools/refactoring/check.sh d69429bd --quick` で、リポジトリのすべてのプログラムの C、出力、終了コードを比べる。
* 計測値: 行数が変わる。`measure.sh --record` で記録し直す。
* カバレッジ: 新しい行と、残した腕が、テストで実行されることを、`coverage.sh --unexecuted --check` で確かめる。

== 範囲外

* 型検査の字句環境（`lib/LexEnv.ml`）。変数をリストで持ち、`push_var` と `get_var` が先頭から探す。1つの関数の中の変数の数の2乗で遅くなる。いまは、これが `variables-in-main` の伸びを決めている（「実装の記録」）。別の issue にする。
* `if` 文、`case` 文、ループの後で、表全体を比べること。1回が変数の数に比例するので、`if` 文を変数ごとに置いた関数は、変数の数の2乗になる。分岐の中で変わった行だけを比べれば減らせるが、比べ方を変えることになる。
* 1つの式が多くの変数を使うとき、`combine_by_variable` は、部分の表を合わせるたびに、表のすべての変数を見る。引数に変数を V 個並べた呼び出しは、V の2乗になる。前は、表のすべての変数ごとに式をたどったので、これより遅かった。
* issue の「ほかに残っている、線形に走査する処理」（`store_function_body`、`register`、`get_union`、`get_typeclass`、評価順の固定）。
* `lib/LinearityCheck.ml` は 600 行を超え、関数を多く持つ。AGENTS.md の分け方に合わせるのは、別のリファクタリングにする。

== セルフレビュー

issue の本文に照らして見直した。

* 「`check_expr` が、式ごとに、スコープにある全変数を調べる」: 式が使う変数だけを調べる。
* 「`get_entry` は、そのたびに表を走査する」: 表を名前から引く。
* 「match の腕が、どのテストからも実行されなくなる」: `Zero` を型から消した。
* 呼び出し元: 表を作り、変える関数は、このファイルの中だけにある。`LinearityCheck.mli` は `state_tbl` を抽象型として出すだけで、ほかのファイルは表に触れない。単体テスト（`test/UnexecutedCheckerTest.ml`）は、内部エラーの文面に表の中身（`Entries:` の後の行）を固定している。`show_state_tbl` は、同じ順で同じ形に書く。
* 見直しで足したこと: `if-after-each-variable` の形。`tables_are_consistent` も `get_entry` を変数ごとに呼ぶので、同じ原因で3乗になっていた。表を名前から引けば、こちらも直る。

== 実装の記録

計画のとおりに実装した。

=== 速さ

前（`d69429b`）と後のコンパイラを、交互に5回ずつ実行した。コンパイル全体の利用者 CPU 時間の中央値で、括弧の中は最小と最大である。
ほかの作業が同じ機械で動いていて、負荷は 4 コアに 10 から 14 だった。交互に実行したので、負荷は両方に同じようにかかる。

[cols="2,1,2,2"]
|===
| 形 | N | 前 | 後

| `variables-in-main` | 200 | 0.088 秒 | 0.075 秒
| | 400 | 0.202 秒 | 0.137 秒
| | 800 | 0.889 秒（0.821 から 1.023） | 0.310 秒（0.227 から 0.358）
| | 1600 | 4.890 秒（4.514 から 5.115） | 0.776 秒（0.729 から 0.846）
| | 3200 | 測っていない | 2.102 秒（1.955 から 2.313）
| `function-per-type` | 800 | 0.290 秒 | 0.272 秒
| | 1600 | 0.647 秒（0.562 から 0.694） | 0.713 秒（0.619 から 0.724）
| | 3200 | 測っていない | 2.246 秒（2.199 から 2.281）
| `if-after-each-variable` | 200 | 0.194 秒 | 0.091 秒
| | 400 | 1.013 秒 | 0.192 秒
| | 800 | 6.812 秒（6.279 から 7.086） | 0.545 秒（0.440 から 0.554）
| | 1600 | 49.679 秒（49.241 から 52.554） | 1.704 秒（1.281 から 1.930）
| | 3200 | 測っていない | 8.283 秒（8.235 から 8.449）
|===

どの形とどの N でも、前と後のコンパイラが書いた C は、sha256 で同じだった。終了コードはどれも 0 である。

`function-per-type` の 1600 個の差は、ばらつきの中にある。callgrind の命令数は、前が 5,895,511,750、後が 5,901,553,790 で、0.1% しか違わない。線形性の検査は、前も後も、命令の 0.2% 弱である。

=== 線形性の検査の命令数

callgrind で、`check_module_linearity` の中の命令数を数えた。

* `variables-in-main` の 800 個: 前は 6,331,679,556（全体の 70.5%）、後は 8,645,907 である。
* 後の `variables-in-main`: 800 個で 8,645,907、1600 個で 16,842,903（全体の 0.27%）。2倍にすると 1.95 倍で、変数の数に比例している。
* 後の `if-after-each-variable`: 800 個で 126,637,020（2.75%）、1600 個で 447,766,747（3.12%）。2倍にすると 3.5 倍である。ほとんどは `tables_are_consistent` の中の `trim_free` で、`if` 文ごとに表のすべての行を見る。範囲外に書いた、表全体を比べる処理である。

=== 残っているもの

後のコンパイラの伸びを決めているのは、型検査である。`variables-in-main` を 800 個から 1600 個にすると、命令数は 2,656,007,934 から 6,259,562,896 になる（2.36 倍）。部分ごとの伸びは次のとおりである。

* `LexEnv.get_declared_var`: 3.98 倍（1600 個で全体の 17.6%）。`LexEnv.push_var`: 4.0 倍。型検査の字句環境が、変数をリストで持つからである。
* `TypingPass.augment_module`（上の2つを含む）: 3.5 倍。
* 単相化（`Monomorphize.monomorphize`）: 2.14 倍。コード生成（`CodeGen.gen_module`）: 2.11 倍。

`if-after-each-variable` の 1600 個では、`LexEnv.get_declared_var` が全体の 30.7% を占める。

`function-per-type` も、1600 個から 3200 個で 3.1 倍になる。線形性の検査は 0.2% 弱なので、この issue の外の原因である。issue の「ほかに残っている、線形に走査する処理」が候補である。

=== 確認の結果

* `tools/refactoring/run-every-ci-check-locally.sh` の 14 個の検査は、すべて `ok` だった。`every-line-is-executed` も通る。残した腕は、どれもテストが実行する。
* `tools/refactoring/check.sh d69429bd --quick`: リポジトリの 3043 個のプログラムで、C、出力、終了コードの違いは 0 だった。
* `lib/LinearityCheck.ml` は 659 行から 642 行になった。`measure.sh --record` で記録し直した。
